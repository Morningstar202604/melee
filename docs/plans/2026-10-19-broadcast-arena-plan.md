# 转播台计划：AI 对抗赛事的观战层重构

- 文档版本：v1.0
- 日期：2026-10-19
- 状态：待评审
- 关联仓库：本目录上级 `melee/`（被重构对象）
- 定位一句话：**不做竞技场，做转播台。规则引擎全部复用现成开源件，只自研"怎么播"。**

---

## 0. 这份文档解决什么问题

现有 `melee` 已证明方向成立（多模型对抗、五赛场、实时事件流、BYOK 安全模型都跑通了），但产品形态有结构性缺陷：

1. 胜负来自不可验证的主观打分，"比赛"没有可读状态，也没有翻盘。
2. 五个赛场本质是五个 prompt 模板，不是五个游戏。
3. 观战界面是"并排的打字机"，没有舞台、没有镜头、没有解说、没有回放。
4. 单场即全部，没有赛季、没有角色、没有宿敌，观众没有理由追。

本计划放弃在旧结构上修补，重新定义产品骨架：**引擎层全部外采，镜头层完全自研。**

### 1.1 "AI 互相对抗"是红海

| Agent 综合 benchmark | THUDM/AgentBench | 3,783★ · Apache-2.0 | ICLR'24 |

| 骗术与嘴炮 | lechmazur/step_game | 92★ · 无许可证 | 赛制设计极佳 |

| 谈判桌 | ed-donner/outsmart | 57★ · MIT | 内心里话面板 + 跨局榜单 |

**结论：造引擎没有空白，做转播没有对手。**

### 1.2 为什么转播层是空白

1. 做引擎的是研究者，关心可复现与统计显著，界面是 `print()` 或 Gradio 默认样式。
2. 做界面的是 demo 作者，几天搭一个 Streamlit，验证完就走，不留赛季、回放、剪辑。
3. 转播是内容工业的活（导播、解说、高光、叙事），与 ML 工程不是同一批人、同一套技术栈。

### 1.3 竞争风险

| 风险 | 影响 | 应对 |
|---|---|---|
| Kaggle Game Arena 把观战界面做起来 | 直接吃掉"评测型对战"市场 | 不与它比权威性，只比娱乐性；它是评测页，我们是节目 |
| TextArena 官方出观战前端 | 我们的引擎层被商品化 | 我们的价值在导演/解说/赛季，不在引擎；被商品化反而降低成本 |
| 模型厂商自己做对抗节目 | 流量被吸走 | 我们的差异是跨厂商、可自托管、可 BYOK |

## 2. 产品定义

### 2.1 一句话

**观众打开一个网页，看两个（或多个）AI 在一条固定规则下打一场有状态的比赛：赛前知道它们各自握着什么秘密，赛中看着它们犹豫、诈唬、失误，赛后拿到一句话战报和 30 秒高光。**

### 2.2 与旧产品的差异

| 维度 | 旧（melee） | 新（本计划） |
|---|---|---|
| 胜负来源 | 裁判主观打分（软场） | 引擎确定性判定；裁判只在需要时做解说/单项奖 |
| 模型输出 | 自由长文 | 结构化动作（JSON Schema 约束）+ 台词 |
| 观战单位 | 事件流 + 卡片列表 | 16:9 舞台 + 导播镜头 + 解说条 |
| 时间 | 只有直播 | 直播 + 可拖动回放 + 变速 |
| 留存 | 单场 | 赛季、角色、战绩、宿敌 |
| 二次传播 | 无 | 自动高光切片 + 一句话战报 |
| 规则 | 五个 prompt 模板 | TextArena 现成游戏环境 |

### 2.3 明确不做

- 不做通用评测平台，不发布 leaderboard 权威分。
- 不做"五个赛场"式的横向铺开，一次只做一个游戏。
- 不做自由文本当动作。
- 不让 LLM 当主裁判决定胜负。
- 不做匿名单场（观众必须知道谁是谁，角色是叙事资产）。
- 不在第一版引入 Remotion（许可证与成本另议，见 §9）。

## 3. 架构

### 3.1 进程与仓库形态

```
repo/
├─ services/
│  └─ match/            Python 3.12 + FastAPI + sse-starlette + TextArena
│     ├─ engine/        游戏适配层（把 TextArena env 包成事件）
│     ├─ agents/        选手适配器（provider 无关，JSON 动作约束）
│     ├─ narration/     解说模型（只读事实，不参与判定）
│     └─ season/        赛程、积分、角色档案
├─ packages/
│  └─ contracts/        事件 JSON Schema（单一真相源）→ 生成 pydantic / zod
├─ apps/
│  ├─ web/              React 19 + Vite + TypeScript（观众端）
│  └─ director/         React（复用 web 组件，导播台）
└─ services/
   └─ clips/            高光切片（第一版 MediaRecorder，见 §9）
```

### 3.2 数据流

```
选手模型 ──动作 JSON──> 引擎 ──事件──> 事件日志（append-only）
                                          │
                                          ├─> SSE ──> 观众端 reduce() ──> 舞台
                                          ├─> 解说模型（读事实）
                                          ├─> 赛季统计
                                          └─> 高光切片
```

三条铁律：

1. **事件日志是唯一真相。** 任何 UI 状态都能由 `reduce(events)` 重算出来。
2. **直播与回放共用同一套投影。** 直播 = 追加事件；回放 = 从任意 offset 重放。
3. **导演决策也是事件。** 镜头切换写入日志，回放时镜头完全一致。

### 3.3 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 观战前端 | React 19 + Vite | 实时应用不是网站；不需要 SSR/RSC；Vite 产物是静态文件，CDN 可托管 |
| 动画 | Motion 14 | 布局动画、FLIP、编排序列，转播感的主力 |
| 图表 | ECharts 6 | 胜率条、雷达、时间轴；Apache-2.0 |
| 状态 | Zustand 5 + 纯 reducer | 回放与直播共用投影，不引入 XState |
| 舞台渲染 | DOM + CSS transform；PixiJS 仅在精灵/粒子密集时引入 | 文字类比赛 95% 画面是卡片与棋子，DOM 足够且可调试 |
| 比赛服务 | Python + FastAPI | TextArena 是 Python 生态，强绑 |
| 传输 | SSE + REST | 单向广播足够；代理友好、自动重连；无需 WebSocket 双向能力 |
| 契约 | JSON Schema → 双端生成 | 手写两遍必然漂移 |

**不选 Next.js 的理由**：观战页是一个永不刷新的实时视图，Next 解决的问题（SEO、首屏 SSR、一体化部署）在此价值极低，而带来的约束（RSC 边界、canvas 类库打包、跨源配置）已经在旧项目里踩过。若未来确实需要分享页的 OG 卡片，单独做一个静态生成的小站即可。

**不选 Vue/Svelte 的理由**：Svelte 5 的细粒度响应式确实适配高频更新，但 ECharts/Motion/Pixi 的封装生态明显偏 React。

## 5. 事件契约

### 5.1 设计原则

1. 事件是**事实**，不是 UI 指令。UI 想怎么画由前端决定。
2. 每个事件带单调递增 `seq` 与 `matchId`，支持 `Last-Event-ID` 续传。
3. 事件必须可序列化为 JSON，禁止携带函数、Date 对象、undefined。
4. 观众视角与选手视角分离：同一事件对观众可全量，对选手需裁剪（见 §5.3）。
5. 契约以 JSON Schema 为单一真相源，生成 pydantic 与 zod。

### 5.2 事件类型（第一版 12 种）

| 事件 | 关键字段 | 说明 |
|---|---|---|
| `match.created` | matchId, game, players[], seed, config | 建场 |
| `match.started` | startedAt, firstPlayer | 开赛 |
| `round.started` | round, activePlayers[] | 轮次开始 |
| `turn.started` | player, deadlineMs | 轮到某人 |
| `thought.delta` | player, text | 思考流（可选、可关闭） |
| `action.proposed` | player, action, raw | 模型提出的动作 |
| `action.rejected` | player, reason, retryable | 非法动作，是游戏事件 |
| `action.applied` | player, action, effects[] | 合法动作及结算 |
| `state.changed` | publicState, deltas[] | 公开状态变化（HUD 用） |
| `narration.line` | text, tone, refs[] | 解说词，附事实引用 |
| `match.ended` | winner, reason, finalState | 终局 |
| `director.cue` | shot, target, durationMs | 导播决策（回放一致性的关键） |

可选第 13 种：`audience.reaction`（聚合后的观众押注/投票快照，不含个人身份）。

### 5.3 可见性

```ts
type Visibility = 'public' | { players: string[] }
```

- `thought.delta` 默认 `public`（观众看得到选手的犹豫，这是产品卖点）。
- 隐藏信息（如狼人身份、对手手牌）通过 `observe(state, player)` 裁剪，**不进入该选手的 observation**。
- 服务端在发出事件前做一次可见性过滤；前端不做安全判断。

### 5.4 事件样例

```json
{
  "seq": 42,
  "matchId": "m_20261019_001",
  "type": "action.applied",
  "at": "2026-10-19T12:00:03.412Z",
  "player": "p1",
  "action": { "kind": "ask", "question": "Is it alive?" },
  "effects": [{ "kind": "answer", "value": "Yes" }]
}
```

### 5.5 事件日志与快照

- 日志 append-only，落 SQLite（`events` 表：match_id, seq, type, payload, at）。
- 每 N 条事件或每轮结束写一份 `snapshot`（状态投影），加速回放定位。
- 回放 = 最近快照 + 之后的事件重放；无需从头 reduce。

## 6. 观战端设计

### 6.1 舞台

- 固定 16:9（1920×1080 设计稿），等比缩放居中，留黑边。
- 所有构图在舞台内完成：比分牌、下三分之一字幕、解说条、镜头。
- 好处：构图可控；截图即海报；未来导出视频可直接复用同一套组件。

### 6.2 五个常驻面板

| 面板 | 内容 | 技术 |
|---|---|---|
| 舞台 | 棋盘/牌桌/线索板，动作可视化 | DOM + Motion；密集精灵时 PixiJS |
| 记分牌 | 血量、筹码、剩余回合、领先者 | HUD，数字滚动动画 |
| 内心戏 | 选手思考流，默认折叠，关键时刻自动弹出 | 前端控制打字节奏，不透传网络分片 |
| 洞察层 | 胜率条、诈唬指数、观众押注分布 | ECharts + 本地叠加 |
| 解说条 | 一句话点评，走字幕位 | 独立解说模型，不参与判定 |

### 6.3 双时钟

- **直播时钟**：跟随 SSE 最新事件，显示 `LIVE` 标记。
- **回放时钟**：拖动时间轴即进入回放，可 0.5x–4x 变速，可点"回到直播"。
- 两者共用 `reduce(events)`，只是输入的事件前缀不同。

### 6.4 死时间处理

AI 一步需要数秒，这是最难看的根源。处理办法：

1. 思考面板实时刷字，让观众看见犹豫。
2. 押注条在倒计时中跳动，给观众事做。
3. 关键回合前 1–2 秒"揭晓延迟"，制造悬念。
4. 隐藏信息只对观众可见，形成戏剧反讽（必须由 UI 主动呈现，不能等赛后揭晓）。

### 6.5 无障碍与性能

- 颜色不作为唯一状态指示（领先/落后同时用图标与文字）。
- `prefers-reduced-motion` 时关闭编排动画。
- 高频事件用 rAF 合帧，一帧一次 React 提交（复用旧项目 battle-store 的经验）。
- 长对局虚拟化：舞台只渲染当前与相邻轮次。

## 7. 导演与解说

### 7.1 导演系统

导演是**规则 + 可选人工**的组合，不是又一个 LLM：

| 镜头 | 触发条件 |
|---|---|
| 广角 | 默认 |
| 特写 | 某选手连续两回合无进展 / 关键动作前 |
| 内心戏插入 | 思考流出现高信息量片段（长度、问号、否定词） |
| 揭晓 | 隐藏信息即将公开 |
| 慢镜 | 终局前最后一步 |

- 自动导演用确定性规则（可测试），人工导播台可覆盖。
- 每个决策产出一条 `director.cue` 事件，回放完全一致。

### 7.2 解说系统

- 独立模型，输入只有"已发生的事实"（事件 + 状态投影），不输入选手隐藏信息。
- 输出短句，带 `refs[]` 指向事件 seq；前端可点击回溯。
- **事实校验**：解说中的数字、动作名必须在事件里存在，否则丢弃该句。
- 明确不参与判定，避免"裁判兼主持人"的可信度塌方。

## 8. 赛季与角色

### 8.1 角色

- 每个模型一个角色：名字、头像、人设一句话、战绩、头衔。
- 角色不是模型本身，是"这个模型在这个赛季的身份"，可换模型重开赛季。

### 8.2 赛程

- 循环赛 → 季后赛。
- 积分优先用 OpenSkill（多对局更稳），Elo 仅作展示。
- 每场结束后更新：胜率、连胜、宿敌关系（交手次数与胜负差）。

### 8.3 call-back

- 每场开赛前，向选手注入一份极短档案：上次输给谁、说过什么。
- 档案进入提示词，制造连续性；长度上限固定，避免上下文膨胀。

## 9. 高光切片

### 9.1 第一版：浏览器端录制

- 用 `MediaRecorder` 录 canvas / DOM 截图序列，产出 15–30 秒 WebM。
- 零许可风险、零服务端成本，缺点是画质与排版受限于录制时窗口。

### 9.2 第二版：服务端渲染（待评估）

- Remotion 4.0.536 许可证：个人、≤3 员工的营利组织、非营利组织免费；超规模需付费。
- 若届时组织规模仍在免费范围，可直接用；组件与 `apps/web` 共用。
- 若超出，改用 FFmpeg + 服务端 canvas 逐帧渲染，或直接购买许可。

### 9.3 切片策略

- 从事件日志找"转折点"：领先易手、非法动作、隐藏信息揭晓、最后一手。
- 每个转折点前后各取 8 秒，最多 3 段拼接。

## 10. 里程碑

### M0：契约与骨架（1 周）

交付：
- `packages/contracts` JSON Schema + 生成脚本。
- `services/match` 能跑通 TextArena 的 `TwentyQuestions`，输出 12 类事件到 SQLite。
- 两个假选手（脚本化 agent）完成一整局。

验收：
- 事件 `seq` 严格单调，无空洞。
- 任意 offset 重放得到相同终局。
- 单测覆盖：状态机、非法动作、隐藏信息不泄漏。

### M1：可看的直播（2 周）

交付：
- `apps/web` 舞台 + 记分牌 + 内心戏 + 解说条。
- SSE 直播、断线重连、`Last-Event-ID` 续传。
- 两个真实模型对局可完整观看。

验收：
- 首屏 2 秒内出画面。
- 断网 10 秒后恢复，不丢事件、不重复。
- 舞台在 1280×720 与 2560×1440 下构图不变形。

### M2：回放与导播（2 周）

交付：
- 时间轴、变速、回到直播。
- 自动导演规则 + `director.cue` 事件。
- 导播台（人工覆盖）。

验收：
- 同一场比赛，回放与直播的画面序列完全一致。
- 导播规则有单测；每条 cue 可追溯触发条件。

### M3：赛季（2 周）

交付：
- 角色档案、循环赛、积分、宿敌。
- 赛前档案注入。

验收：
- 一个 8 人循环赛可完整跑完并出榜。
- 积分更新可重算（幂等）。

### M4：高光与传播（1 周）

交付：
- 转折点识别 + 30 秒 WebM 导出。
- 一句话战报模板。

验收：
- 导出视频包含至少一个转折点，时长 15–30 秒。
- 战报不含未发生的事实（人工抽检 20 场）。

**总工期估算：8 周（单人全职，含缓冲）。**

## 12. 第一版游戏选择

优先级从高到低：

1. **TwentyQuestions（二十问）**：规则极简、天然戏剧反讽（观众知道答案）、每回合输出短、TextArena 已有实现。最适合验证观战层。
2. **SecretMafia / 狼人杀**：多人、隐藏身份、嘴炮，观赏性最强，但信息隔离与轮次复杂度高。
3. **Codenames**：团队对抗、语义联想，画面感强。
4. **Negotiation / 谈判**：金币分配，能出"AI 有多贪"的名场面。

**第一版只做 TwentyQuestions。** 跑通后再评估第二个。
