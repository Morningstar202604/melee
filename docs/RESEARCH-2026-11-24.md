# AI 对抗观赛平台：行业基线与 3D 可行性调研

日期：2026-11-24
范围：通用 AI 测评平台、开源多智能体/对抗工具、AI 对局数据集与 3D 渲染栈
结论用途：为 melee 1.10.0 的“赛事级观赛 + 教练级实时干预 + 3D 场景”定位提供可追溯依据。本文只做调研与路径论证，不复制任何竞品代码或界面。

## 1. 结论先行

1. **测评平台回答“谁更强”，melee 回答“这一局发生了什么、为什么、教练能否改变”。** HELM、OpenCompass、Artificial Analysis 的核心产物是分数、排名、成本/速度曲线；它们不以单场对抗的实时观赛为单位。melee 不应该把自己做成第四个排行榜。
2. **开源生态里已有成熟的“环境/规则”和“对局数据”，但缺少“观赛转播层”。** PettingZoo 提供多智能体环境 API，TextArena 提供可运行赛制，Kaggle Game Arena 提供真实对局样本；它们都不负责“把一局对抗变成可看、可干预的赛事画面”。
3. **3D 可行，但只能作为表现层。** Three.js + OrbitControls 足以完成棋盘、选手 pod、镜头和动效；它不能成为第二套真相。所有画面必须从同一份 append-only 事件流重算，WebGL 失败时必须退回 2D。
4. **差异化锚点不是“3D 本身”，而是“观赛视角透明化 + 教练级实时干预”。** 3D 只是让空间关系、选手存在感、回合节奏更容易被看懂；真正不可替代的是：观众能看到思考与动作的因果链，教练能在回合节点下达指令且指令会被记录、排队、投递、验证。

## 2. 对标对象与口径

| 类型 | 对象 | 为什么看它 | 不看什么 |
|---|---|---|---|
| 学术评测 | HELM | 标准化、多场景、可复现的模型评测范式 | 不做它的榜单复刻 |
| 中文评测 | OpenCompass | 中文/多模态评测体系与平台化组织方式 | 不把评测集接进赛事主链路 |
| 商业分析 | Artificial Analysis | 模型速度、价格、质量的独立对比与呈现 | 不做模型采购决策页 |
| 多智能体环境 | PettingZoo | AEC/并行环境 API、第三方环境接入方式 | 不替代自有引擎 |
| 对抗环境 | TextArena | 可直接运行的文本对抗赛制 | 不把上游规则改成自有规则 |
| 社交推理研究 | Werewolf Arena | LLM 社交推理对局的研究范式 | 不复制其 demo 界面 |
| 真实对局数据 | Kaggle Game Arena | 真实 chess 对局与可回放样本 | 不把数据集当自有内容 |
| 3D 渲染 | Three.js | WebGL 场景图、相机、材质、性能边界 | 不引入游戏引擎 |

## 3. 通用 AI 测评平台扫描

### 3.1 HELM（Stanford CRFM）

HELM 的价值在于“同一套标准化流程跑多场景、多指标”，强调可复现与透明。它的基本单位是 **benchmark / scenario / model**，产物是聚合指标与对比表；没有“单场对抗直播”这个对象。可复用的是评测方法论：固定配置、公开提示、可重跑；不可直接复用的是它的场景注册与指标体系。

来源：<https://crfm.stanford.edu/helm/>、<https://crfm-helm.readthedocs.io/en/latest/>

### 3.2 OpenCompass

OpenCompass 把中文/多模态评测做成平台化产品：数据集、模型、榜单、评测流水线。它解决的是“如何系统地比较模型”，不是“如何看一场比赛”。它的平台化组织（任务编排、结果沉淀、可视化榜单）可以借鉴，但 melee 的实时事件流、回合调度、教练干预不在它的产品边界内。

来源：<https://opencompass.org.cn/>

### 3.3 Artificial Analysis

Artificial Analysis 以独立分析的方式对比模型的质量、速度、价格，适合采购与选型。它把“模型”当商品参数来比较，不把“对局过程”当内容。melee 与它的关系是互补：赛前可以用它选模型，赛后用 melee 看这局为什么赢/输。

来源：<https://artificialanalysis.ai/models>、<https://artificialanalysis.ai/#speed>

### 3.4 测评平台的共同边界

- **对象**：模型或模型组合，不是一局具体对抗。
- **时间**：批量跑分，非实时直播。
- **用户角色**：评测者/采购者，不是观众/教练。
- **产物**：分数、排名、置信区间、成本曲线，不是叙事、镜头、可干预的回合。
- **真相来源**：聚合结果，不是逐事件日志。

这五点就是 melee 的场景边界：不跟它们抢“谁更强”的结论，专注“这局怎么发生”。

## 4. 开源 AI 对抗工具扫描

### 4.1 PettingZoo

PettingZoo 是多智能体环境的通用 API（AEC 与并行两种模式），提供环境注册、第三方环境接入、标准 reset/step/observe 语义。它适合做“规则与智能体的接口”，不提供观赛 UI、转播、教练席。melee 对它的正确姿势是：把赛制适配成统一 observation/legal action 接口，渲染与调度留在自有链路。

来源：<https://pettingzoo.farama.org/main/release_notes/>、<https://pettingzoo.farama.org/environments/third_party_envs/>、<https://pypi.org/project/pettingzoo/>

### 4.2 TextArena

TextArena 提供可运行的文本对抗环境，melee 以可选依赖方式接入，注册了 12 个赛制。它的优势是“规则确定性、环境可复现”；短板是“没有赛事级的观赛与干预层”。melee 复用它的环境能力，不把它当运行时强依赖；缺失时只保留内置赛制。

来源：<https://pypi.org/project/textarena/>（版本与许可证见仓库 `NOTICE`）

### 4.3 Werewolf Arena

Werewolf Arena 把狼人杀这类社交推理做成 LLM 对局研究，关注说服、欺骗、协作等社会能力。它证明“社交对抗”可以作为评测对象，但公开资料的重点是研究与对局分析，不是实时观赛产品。melee 可借鉴其角色/发言/投票的结构化事件，不复制其界面或提示词。

来源：<https://arxiv.org/pdf/2407.13943>

### 4.4 Kaggle Game Arena

Kaggle Game Arena 的 chess 对局数据提供了真实模型对抗的逐步记录，melee 1.9.10 已把它作为导入源，保留来源、许可证、棋盘与走子。它解决“有真实对局可看”，不解决“实时干预”。这也说明 melee 的导入能力是内容入口，不是核心护城河。

来源：<https://www.kaggle.com/datasets/kaggle/chess-text-gameplay>

**矩阵读法**

- 测评平台的“强”在聚合与可比，melee 的“强”在单场叙事与干预；不是同一竞争维度。

## 6. 场景边界：为什么不是“第四个排行榜”

| 维度 | 测评平台 | melee |
|---|---|---|
| 分析单位 | benchmark / 模型 | 单场 match / 单回合 |
| 时间形态 | 批处理、离线 | 实时流 + 可回放 |
| 主要用户 | 研究者、采购者 | 观众、教练、赛事运营 |
| 核心问题 | 谁更强、贵不贵、快不快 | 这局发生了什么、为什么、能否改变 |
| 真相来源 | 聚合结果 | append-only 事件日志 |
| 成功标准 | 排名稳定、可复现 | 观赛流畅、干预可解释、赛后可信 |
| 3D 的角色 | 基本不需要 | 空间关系与选手存在感的表达层 |

**定位一句话**：melee 是 AI 对抗的“转播 + 教练席”，不是 AI 能力的“考试院”。

## 7. AI 全链路对抗可视化 + 3D 可行性路径

### 7.1 数据路径

```
引擎/导入 → append-only events → reducer/视图状态
                              ├─ 2D watch（棋盘、时间轴、思考流）
                              ├─ 3D arena3d（Three.js 场景）
                              ├─ /scene 快照（OBS/第三方）
                              └─ 战报/高光（同一事件派生）
```

3D 页面只消费 `events` 与 `/scene`，不直接读引擎内部状态。这样直播、回放、OBS、3D 的画面可以互相对账；任何一方出现分歧，以事件日志为准。

### 7.2 场景映射

- **棋盘**：事件里的 `gameState.board` 转成瓦片网格；8×8 加坐标，3×3/6×6 自适应；无棋盘赛制改为全息核心舞台。
- **棋子**：字形/单词 Sprite，移动用 620ms 缓动，吃子用 300ms 缩放淡出；同一 `glyph` 的就近匹配避免“整盘重建”。
- **选手**：围绕舞台的 pod + 光束 + 名牌；数量随赛制变化，颜色按选手索引。
- **镜头**：broadcast / top / side / free / auto orbit 五种；预设用 620ms 缓动，自由镜头交给 OrbitControls。
- **信息层**：2D HUD 与 3D HUD 共用 i18n 键；教练指令、事件数、最后一手、子力差、解说同步更新。

### 7.3 技术选型

- **Three.js 0.187.0（MIT）**：WebGL2 场景图、材质、Sprite、阴影、色调映射；vendor 到 `apps/web/vendor/three/`，无构建链。
- **OrbitControls（MIT）**：拖拽/缩放/平移；镜头预设仍由自有逻辑控制，避免第三方接管产品镜头语义。
- **不引入游戏引擎**：Unity/Godot 的体积、构建链、部署复杂度与“单端口自托管”冲突；本项目的 3D 需求是“可读的赛事舞台”，不是可交互游戏。

### 7.4 性能与体积

- 设计目标：1600×1000 视口 60fps；draw call 控制在百级；纹理只用于文字 Sprite，避免大图集。
- 实际 vendor 体积：`three.module.js` 约 644KB + `three.core.js` 约 1.5MB + `OrbitControls.js` 约 40KB（未压缩，随服务静态托管）。
- 降级：WebGL2/WebGL 不可用时显示“2D 转播仍然可用”，不白屏、不循环报错。
- 可访问性：canvas `aria-hidden`；HUD 文本可读；`prefers-reduced-motion` 关闭过渡；保留“返回 2D”。

### 7.5 风险与未验证项

| 风险 | 影响 | 当前处置 |
|---|---|---|
| 无 GPU/禁用 WebGL | 3D 不可看 | 预检 + 明确降级页；2D 全功能 |
| 移动端 GPU/发热 | 掉帧 | 限制 pixelRatio ≤2；后续做 LOD/降级画质 |
| 大棋盘/长对局 | 场景对象多、动画多 | 只保留可视对象；后续分页/裁剪 |
| import map 与 CSP | 脚本被拦截 | CSP `sha256` 白名单 + 静态测试校验 hash |
| 第三方升级 | 视觉/接口回归 | vendor 固定版本；升级单独提交并跑 3D 截图 |
| 无头环境 WebGL | 自动化截图失败 | 用 SwiftShader 软件渲染做视觉验收；不作为生产依赖 |

### 7.6 落地阶段

- **P0（1.10.0，已完成工作树）**：棋盘/选手/镜头/HUD/动画/降级；2D 与 3D 共用事件流；教练席双入口。
- **P1（1.11.x）**：LOD、移动端画质档、场景资产配置、长时间运行内存回收。
- **P2（2.x）**：多桌/多赛场、可编排舞台、裁判/教练多角色权限。

## 8. 可复用与不引入清单

**复用**

- 环境/规则：TextArena（可选）、PettingZoo 的接口思想（不直接引入其 UI）。
- 数据：Kaggle Game Arena（导入，保留 CC BY 4.0 与来源）。
- 渲染：Three.js + OrbitControls（MIT，vendored，不改源码）。
- 评测方法：HELM/OpenCompass 的固定配置、可复现、公开提示思路。

**不引入**

- 不引入完整评测集/榜单系统：会把产品拉回“考试院”。
- 不引入游戏引擎/3D 资产管线：超出“赛事舞台”需求。
- 不复制竞品界面、提示词、数据集内容。
- 不把 Git 仓库当图床/素材库；截图与演示资产走发布包/平台图床。

## 9. 验收指标（1.10.0）

- 12/12 注册赛制在并发压测中完成，0 卡死；24 场与 48 场两档报告可复现。
- 教练指令：目标校验、非直播 409、长度 280、queued→delivered 单次投递、2D/3D 都可见。
- 3D：8×8 首帧即棋盘；3×3/6×6 正常；无棋盘赛制有全息舞台；无 WebGL 有降级页；中英文截图。
- 契约：`coach.message` 在 JSON Schema、Pydantic、Zod、架构路由清单四处一致。
- 发布：全量门禁全绿、版本/CHANGELOG/README/演示包同步、五平台 main 与 tag 对齐。
